# Политика написания скриптов и долгих команд

Канон для всех агентов и скриптов репозитория (и `buildScript/`, и разовых обёрток).
Причина: долгая команда без видимого прогресса выглядит как моргающий курсор —
непонятно, зависла она или работает; обрыв вызова/соединения не должен убивать
процесс и терять результат.

Эталон (общий для всех проектов): `C:\Users\user\projects\IsaevAudio\.kilo\instructions\
long-running-commands.md` — оттуда портирован инструмент `buildScript/long-run.sh`.

## Когда применяется

Любая операция длиннее ~30 с: gradle-сборки, установки, сиды/каталог, мониторы,
длинные диагностики, CI-запуски, сетевые ожидания, всё, что может «зависнуть»
(сеть, adb, docker).

## Канонический механизм: `buildScript/long-run.sh`

Zed/терминал убивает дерево процессов при завершении вызова — `nohup ... &` и
`Start-Process` напрямую из шелла НЕ переживают (проверено в IsaevAudio 2026-08-11).
Рабочий механизм — detached-процесс через PowerShell `Start-Process -PassThru`:

```
bash buildScript/long-run.sh start <name> -- <command...>   # detached: лог в artifacts/<name>.log(.err), pid в artifacts/<name>.pid
bash buildScript/long-run.sh status <name>                  # жив? сколько идёт + хвост лога
bash buildScript/long-run.sh log <name> [N]                 # хвост лога (по умолчанию 20 строк)
bash buildScript/long-run.sh stop <name>                    # taskkill /F /T по pid-файлу
bash buildScript/long-run.sh list                           # все активные
```

Каталог логов — `artifacts/` (переопределяется `LR_ART`). Скрипт сам чинит CRLF и
сам выбирает среду: WSL (opencode/zed) или Git Bash/MSYS.

Правила прогона:

1. `start <name> -- <cmd>` — сразу показать пользователю: что запущено и где лог.
2. Периодически `status <name>` — показывать прогресс, а не ждать молча.
3. Сложные команды (кавычки/пайпы/редиректы) — завернуть в скрипт
   `buildScript/<task>.sh` и запускать `start <name> -- bash buildScript/<task>.sh`.
4. Команда завершилась сама — `status` покажет «НЕ запущен», лог сохранён.
   Ошибка — разбирать по полному логу, не перезапускать вслепую.

## Три обязательных свойства скриптов

### 1. Видимый прогресс (никакого «моргающего курсора»)

- Каждая фаза пишет в консоль: `[12:03:45] шаг 3/7: compileKotlinDesktop`.
- Если шаг длинный (>60 с) — внутри шага периодические строки «жив» (heartbeat).
- Мониторы/ожидания выводят периодический снапшот состояния (каждые 10–30 с),
  а не пустой спиннер.
- Никаких блокирующих чтений: `cat /proc/<pid>/fd/2`, `tail -f` без таймаута —
  это выглядит как зависание.

### 2. Устойчивость к обрыву (resume, а не рестарт)

- Логи — всегда в файл: `artifacts/` (long-run.sh) или `logs/` (самологируемые
  скрипты). Обрыв не теряет историю.
- Скрипт пишет текущую фазу в state-файл (см. шаблон); при перезапуске читает его
  и продолжает с места обрыва.
- Шаги идемпотентны: перед выполнением проверяют «уже сделано» (артефакт/маркер
  существует) и пропускают. Пример: APK уже собран — не пересобирать, а установить.
- `trap` на SIGINT/TERM: записать «прервано на фазе N» в state и лог, выйти с
  понятным кодом. После обрыва: `tail` лога + продолжение с той же фазы.

### 3. Heartbeat-логи

- Формат: `[HH:MM:SS] шаг N/M: <название>`, внутри длинного шага — `... <n> сек, жив`.
- Heartbeat пишется **и в консоль, и в лог** — чтобы человек видел прогресс, а по
  логу после обрыва было видно, где именно упало.
- Если процесс не пишет ничего дольше лимита (по умолчанию 60 с) — считаем зависшим:
  разрешено прервать и перезапустить как самологируемый скрипт.

## Что НЕ делать

- НЕ запускать долгие команды «в тишине» и ждать в одном вызове без таймаута:
  у каждого вызова должен быть `timeout`.
- НЕ `nohup ... &` / `Start-Process` напрямую из шелла — только `long-run.sh`.
- НЕ читать блокирующие потоки процесса (см. выше).
- НЕ фильтровать на лету (`Select-String`, `| head` без нужды) так, что полный лог
  теряется: вывод дублировать в файл (`tee`), в ответ — только нужные строки.
- НЕ делать вид, что процесс завершился, пока `status`/`logs` не подтвердили.
- НЕ молча перезапускать то, что уже частично сделано, — сначала проверить
  артефакты/state, продолжить с места обрыва.

## Что делать при ошибке

1. `stop <name>` (если ещё крутится) → полный лог из `artifacts/<name>.log(.err)`.
2. Найти первую ошибку, исправить, перезапустить через `long-run.sh` заново.
3. Если команда оказалась долгой, хотя ожидалась быстрой, — прервать и перезапустить
   как самологируемый скрипт через `long-run.sh`.

## Шаблон самологируемого скрипта (для `buildScript/<task>.sh`)

```bash
#!/usr/bin/env bash
set -euo pipefail
LOG_DIR="${LOG_DIR:-logs}"
LOG="$LOG_DIR/$(basename "$0" .sh).log"; STATE="$LOG_DIR/$(basename "$0" .sh).state"
mkdir -p "$LOG_DIR"

log()   { echo "[$(date +%H:%M:%S)] $*" | tee -a "$LOG"; }
phase() { echo "$1" > "$STATE"; log "шаг $1/$2: $3"; }
resume() { [[ -f "$STATE" ]] && cat "$STATE" || echo 0; }   # с какой фазы продолжать

trap 'log "ПРЕРВАНО на фазе $(resume)"; exit 130' INT TERM

START=$(resume)
for STEP in $(seq $START 3); do
  case $STEP in
    1) phase 1 3 "build"; [[ -f build/out.apk ]] || ./build.sh | tee -a "$LOG" ;;
    2) phase 2 3 "install"; adb install -r build/out.apk 2>&1 | tee -a "$LOG" ;;
    3) phase 3 3 "smoke"; timeout 300 ./smoke.sh 2>&1 | tee -a "$LOG" ;;
  esac
done
log "ГОТОВО: все шаги выполнены (лог: $LOG)"
```

Идемпотентность — проверкой артефактов (`[[ -f ... ]]`), heartbeat внутри длинных
шагов — периодическим `log "... жив"` (раз в 30 с в цикле ожидания). Затем:
`bash buildScript/long-run.sh start <task> -- bash buildScript/<task>.sh` и
периодически `status <task>`.
