## 3. Разбор цепочки сбоя

**Корневой факт — вечерняя недоступность цели (Telegram) через free-релеи.**
Утром 96% профилей проходили composite messenger, вечером <1%. ПК в том же регионе без VPN не
дотягивает web.telegram.org — целевой ресурс деградирован на пике. Слагаемые: (а) конгестия
бесплатных релеев вечером (пробы в лимит 5–8с не укладываются); (б) Telegram троттлит
датацентровые IP-диапазоны (503); (в) иранские exit'ы блокируют Telegram нативно (Telegram в Иране
заблокирован с 2018 — 503 = блок-страница иранского эджа для профиля 15245).

**Цепочка:**
1. MERGED 4096: TCP 161/2560 alive → URL 0/161 → `prepare_wl_no_url_ok` → revival watch (корректно).
2. Watch прерван → `wl_to_open` fallback: OPEN-пул 256 с `wlUrlProbe=false` — URL-верификация
   open-сетом (telegram+gstatic+connectionTestURL+cloudflare на CONFIRM), успех по ЛЮБОМУ URL.
   15245:200 — почти наверняка gstatic/cloudflare (все composite-пробы окна `web=fail`; у самого
   15245 composite-проба в 19:55 `web=fail`). На WL-аплинке это ничего не доказывает про Telegram.
3. Post-connect WL PRIMARY = только `web.telegram.org` → 503 ×3 → PostConnectExhausted.
   503 получен ЧЕРЕЗ туннель — транспортно туннель жив, отказал Telegram-эдж для exit IP.
4. Recovery: strictFreshFallback требует свежих url-verified резервов — 7 tcp-alive без urlOk
   не годятся (`queueLive=0`, dead=0 jail=0) → `fallback_exhausted` → полный свип заново.
5. **Цикл адаптаций:** `ADAPT_PREPARE_TIMEOUT_MS=30s` обрывает каждый полный свип (первый занял
   128с). Каждый следующий свип стартует с lkg_preseed и повторяет первые ~60–90 кандидатов —
   прогресс URL-фазы не персистится (в отличие от TCP-`wl_sweep_cache`). 6+ свипов без результата.
6. 22:12:54 свип находит 35531 (5589ms при лимите пробы 6с — маргинально) → `wl_adapt_restart`.
   Connect-путь НЕ скипает дублирующий manual probe (адапт-путь не ставит
   `markPrepareVerifiedForConnect`) → через 8с та же проба `web=fail` → `manual_profile_probe_failed`
   → очередь пуста → Stopped с сообщением «Выберите другой профиль…» при АКТИВНОМ автоподборе.

## 5. Ответы на вопросы ТЗ

1. **Почему post-connect проверяет только web.telegram.org (DC 91.105 не участвует):** R1.
   `probeUrlPlan(PRIMARY, wl)` = `primaryBsProbeUrls()` = [web]; даже при попадании в
   `probeMessengerWave` DC пробивается только после web-ok.
2. **Почему 503 на messenger-URL — жёсткий fail:** по дизайну и по тестам
   (`SimpleModeHealthRouteTest.telegramProbeNeverSyntheticEvenOn503`,
   `messengerProbeFailuresAreConclusive`): `isProbeFailureInconclusive` (:357) короткое замыкание
   на messenger-URL ДО ветки 503-транзиента; `wlUrlProbeTreatAsOk` (:426) исключает messenger из
   synthetic-pass. Обоснование верное (на WL Telegram — единственная цель; synthetic = zombie
   Connected), но ретрай-цикл post-connect сам считает 503 транзиентом (`probeUrl=""` в
   `SimpleModePostConnectHealth.kt:95`) — несогласованность: 3 ретрая ≈12с впустую при стабильном 503.
3. **Почему после wave-2 (CONFIRM) post-connect в PRIMARY:** `postConnectProbeUrls()` жёстко PRIMARY
   (R4); wave-2 CONFIRM был на OPEN-пуле (open-URL-сет, не telegram). Плюс контекст волны не
   передаётся из prepare в post-connect.
4. **Соотношение с дизайном:** R1–R4. Uplink reachability direct-only соблюдён. CONFIRM-тир WL
   (instagram+facebook) в post-connect при 503 недостижим; вечером instagram на ПК тоже в таймауте —
   не помог бы.
